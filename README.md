# incremental-ingestion-engine-go

一套本地可运行的增量数据摄入与落地流程：用本地文件模拟数据源（JSONL 变更流水）与目标端（JSON 快照 + 死信文件），保证在**重复消费、位点回退、来源结构变化**下，最终数据状态可预期、可解释。

## 目录结构

```
internal/ingest/
  types.go      事件、操作类型、拒绝原因、重投/对账/结构流水等核心类型
  source.go     本地 JSONL 数据源（行号即位点）
  sink.go       本地目标端：幂等落地 + 死信记录 + 重投冲突检测
  offset.go     位点存储：单调推进、CAS 提交
  schema.go     结构注册表：版本管理、兼容校验、投影、变更流水持久化
  pipeline.go   摄入流水线：采集 -> 校验 -> 投影 -> 落地 -> 提交位点；修复重投
  reconcile.go  结果对账：对齐来源流水、目标端状态与处置结果
cmd/ingestdemo/ 端到端本地演示
```

## 摄入协议

变更事件（`Event`）逐行追加到来源文件，每行一个 JSON：

```json
{"seq":1,"id":"e1","op":"insert","pk":"a","schemaVersion":1,"fields":{"name":"alice","age":30}}
```

- `seq`：来源端单调递增位点；`id`：事件唯一标识（幂等去重）；`op`：`insert` / `update` / `delete`；
- `pk`：主键，必填；`schemaVersion`：事件遵循的结构版本；`fields`：字段载荷（`delete` 可空）。

**校验与拒绝**：坏记录不会被写入死信文件 `deadletter.jsonl`，原因可区分，绝不静默丢弃：

| 原因 | 含义 |
|---|---|
| `missing_pk` | 主键为空 |
| `missing_field` | 必需字段缺失 |
| `type_mismatch` | 字段类型与结构声明不匹配 |
| `unknown_schema` | 事件声明的结构版本未注册 |
| `incompatible_schema` | 载荷含最新结构中不存在的字段（防静默错列） |
| `unknown_op` | 未知操作类型 |
| `pk_conflict` | 修复重投撞上目标端已存在主键且无法凭来源顺序安全判定先后（绝不改写已有数据） |

**幂等落地**：目标端按事件 `id` 去重，且同一主键上 `seq` 不大于已应用值的事件被跳过；死信按 `(id, reason)` 去重。因此同一批数据重复运行后，目标端不重复、不丢失。

## 位点提交规则

- 位点 = 已消费的事件行数，持久化在 `offset` 文件中（写临时文件 + rename，崩溃安全）。
- 提交为 CAS：`Commit(prev, next)` 要求 `prev` 等于当前已提交位点且 `next > prev`。
  - `next <= committed` → `ErrOffsetRegression`（回退，拒绝）；
  - `prev != committed` → `ErrOffsetGap`（跳段/并发竞争失败，拒绝）。
- 并发消费时多个 worker 共享同一 `OffsetStore`：只有赢得 CAS 的提交生效，失败者以最新已提交位点重试，因此**已提交位点只单调推进**。
- 进程中断后重新 `Load()` 即从最近一次已提交位点恢复。

## 结构兼容规则

结构以版本注册（首版本必须为 1，之后每次 +1），演进规则：

| 变化 | 结果 |
|---|---|
| 新增字段且显式声明缺省值（`HasDefault`） | 兼容；老事件与存量行一律回填该缺省值，语义确定且稳定 |
| 新增字段但未声明缺省值 | 拒绝（`ErrIncompatibleSchema`） |
| 删除字段 | 拒绝，错误详情含字段名与版本 |
| 字段改名（删除 + 新增同类型字段） | 拒绝，详情中提示 `possible rename to "..."` |
| 已有字段类型变更、可选改必需 | 拒绝 |

事件落地前会被**投影**到最新结构：缺失的新增字段填缺省值；载荷中出现最新结构之外的字段（来源于已删除/改名字段）时以 `incompatible_schema` 拒绝并进入死信，目标端绝不静默错列。不兼容的演进失败时，错误信息保留字段名、版本等可追溯信息。

**结构变更流水**：构造注册表时传入流水文件路径（`NewSchemaRegistry(path)`），则**所有**注册尝试——包括被判定为不能安全兼容的——都会追加到本地 JSONL 流水（`schema-ledger.jsonl`），每条含版本、字段全集、是否接受及拒绝详情。进程重启后经 `Load()` 恢复，已接受版本重建注册表，全部尝试记录经 `Attempts()` 可查，可用于解释某条记录为何被判 `unknown_schema` / `incompatible_schema`。

## 修复重投

被拒记录在上游修好后，通过 `Pipeline.Resubmit(events)` 重新投递：走与正常消费**完全相同**的校验、投影与落地流程，但不读取来源流水、**不推进已提交位点**。

- **幂等**：同一批修正数据重复提交，已应用的事件 ID 幂等跳过，不产生重复数据；死信按 `(id, reason)` 去重，不会重复堆拒绝记录；位点保持不动。
- **主键冲突边界**：修正记录撞上目标端已存在主键、且其来源位点不晚于该主键已应用位点（无法安全判定先后）时，以 `pk_conflict` 拒绝并记入死信——**绝不改写已有数据，也不静默略过**；位点更晚、可安全判定先后的修正记录正常生效。
- **批内确定性**：同一批里同一主键出现多次时，按 `(Seq, EventID)` 取最大者生效，其余以 `pk_conflict` 拒绝；结果与输入顺序、并发调用无关，重复跑和并发跑结论一致。
- 直接构造的事件会先经 JSON 往返归一化，与来源文件解码的事件保持相同的类型语义。

## 结果对账

`Pipeline.Reconcile()` 对齐来源流水、目标端最终状态与各类处置结果，给出来源中每条记录（按事件 ID 去重）的最终结论：

| 结论 | 含义 |
|---|---|
| `applied` | 已生效（含曾被拒、修复重投后生效的记录——最终状态优先） |
| `rejected` | 被拒，附可区分原因（取该事件最后一次拒绝记录） |
| `skipped` | 已消费但被跳过（同主键上已有更新位点的事件） |
| `pending` | 尚未消费（位点未推进到） |

不在来源流水中的处置记录（如纯重投事件）单列在 `External` 中。对账是持久化状态上的**纯计算**：不修改任何状态，重复运行、并发消费、进程重启之后，同样的输入必然得到一致且可复现的报告；同一事件重复投递只计一次，不会重复计数。

## 本地验证

```bash
# 运行单元测试（覆盖重复消费、并发推进、结构变更、修复重投、主键冲突、
# 结果对账与结构变更流水；日志打印位点、提交顺序与变更流水）
go test ./internal/ingest/ -v

# 含竞态检测
go test ./... -race

# 运行端到端演示
go run ./cmd/ingestdemo
```

演示会在临时目录生成 `source.jsonl`（来源）、`sink.json`（目标端）、`deadletter.jsonl`（死信）、`offset`（位点）、`schema-ledger.jsonl`（结构变更流水），可直接查看最终状态；演示末尾打印一次完整对账报告。
